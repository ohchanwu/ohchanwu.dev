    Online Booking from the Clinic Schedule

    클리닉 일정 기반 온라인 예약

    Solution: The server imports the clinic’s WebPT schedule at five-minute intervals and computes bookable times per therapist; when the data is stale or unsafe, it answers 503 with a reason and the booking page falls back to the request form. Result: Online booking has been live since November 7, 2026; patients save a card with Stripe, and only staff can charge a no-show fee.

    해결: 서버가 클리닉의 WebPT 일정을 5분 간격으로 가져와 치료사별 예약 가능 시간을 계산하고, 데이터가 오래되었거나 안전하지 않으면 사유와 함께 503을 반환해 예약 요청 폼으로 전환합니다. 결과: 2026년 11월 7일부터 온라인 예약을 운영하고 있으며, 환자는 Stripe로 카드를 등록하고 노쇼 수수료는 직원만 청구할 수 있습니다.

    Self-Serve Frontend Publishing

    비개발자를 위한 프론트엔드 배포 체계

    Problem: A non-technical staff member needed to publish site changes with AI agents, without backend or cloud access, while the redirects, analytics, and form fallbacks the Go server handled kept working. Solution: I split the site into its own repository on AWS Amplify behind a Cloudflare Worker and froze its route, form, and link contracts, enforced by Python checks, a browser smoke test, and a CI gate, with a Gitleaks scan required before a change is handed off. Result: Changes now ship through pull requests with Amplify previews: 17 pull requests authored by a clinic staff member were merged this way between October 13 and November 10, 2026.

    문제: 비개발자 직원이 백엔드와 클라우드 접근 없이 AI 에이전트로 사이트를 수정하고 배포해야 했고, Go 서버가 처리하던 리다이렉트와 분석, 폼 폴백은 그대로 지켜야 했습니다. 해결: 사이트를 별도 저장소로 분리해 Cloudflare Worker 뒤의 AWS Amplify로 배포하고, 라우트와 폼, 링크 계약을 고정해 Python 검사, 브라우저 스모크 테스트, CI 게이트로 강제하고, 변경을 넘기기 전에 Gitleaks 검사를 거치게 했습니다. 결과: 지금은 PR과 Amplify 미리보기로 변경이 배포되며, 2026년 10월 13일부터 11월 10일까지 클리닉 직원이 작성한 PR 17건이 이 방식으로 병합되었습니다.

    Outage Recovery and Hardening (postmortem)

    장애 복구 및 하드닝 (사후 보고서)

    Problem: In April 2026, the site went down for 2 hours 54 minutes while EC2 status checks kept passing. Analysis: I ruled out an out-of-memory crash with the systemd journal, and CloudWatch showed the gp3 volume pinned at its 125 MiB/s throughput ceiling. The cause was unindexed admin-dashboard queries on a shared root volume. Solution: After restoring on a fresh instance with no customer data loss, I added CloudWatch alarms, query time limits, log rotation, and indexes found with EXPLAIN. Lesson: Cloud limits fail silently, so they must be monitored explicitly, and internal tools must be treated as production too.

    문제: 2026년 4월, EC2 상태 검사는 정상이었지만 사이트가 2시간 54분 동안 응답하지 않았습니다. 분석: systemd 저널로 메모리 부족 가설을 배제했고, CloudWatch에서 gp3 볼륨이 처리량 한도인 125MiB/s에 막힌 것을 확인했습니다. 원인은 공유 루트 볼륨에서 인덱스 없이 실행된 관리자 대시보드 쿼리였습니다. 해결: 새 인스턴스에서 고객 데이터 손실 없이 복구한 뒤 CloudWatch 알람, 쿼리 실행 시간 제한, 로그 로테이션, EXPLAIN 기반 인덱스를 적용했습니다. 교훈: 클라우드의 한도는 경고 없이 다가오므로 지표로 직접 감시해야 하고, 내부 도구도 프로덕션처럼 다뤄야 합니다.

  • 2026-now
    Jobcron

    Goal: Jobcron gathers entry-level developer postings from Korean job boards into one daily briefing, with an explained fit score for each post. Infra: A Go binary runs as an invite-only beta on EC2 and private RDS managed with Terraform, and its first production deployment was gated on restoring an encrypted backup. It was built through harness engineering with multiple AI agents. AI: The server asks an external question-answering model (TypeSafe Jev) fixed yes/no and scored questions about each post through an API and pays for it under per-user and total daily US-dollar limits, with a deterministic fallback.

    목적: 국내 채용 포털에 흩어진 신입 공고를 매일 하나의 브리핑으로 모으고, 공고마다 근거가 설명된 적합도 점수를 제공합니다. 인프라: Go 바이너리를 Terraform으로 관리하는 EC2와 프라이빗 RDS에 배포해 초대 전용 베타로 운영하며, 첫 운영 배포는 암호화 백업 복원에 성공한 뒤 승인했습니다. 여러 AI 에이전트를 활용한 하네스 엔지니어링으로 개발했습니다. AI: 서버가 외부 질의응답 모델(TypeSafe Jev)을 API로 호출해 공고마다 정해진 예/아니요 질문과 점수 질문에 답하게 하고, 비용은 사용자별, 전체 일일 USD 한도 안에서 서버가 부담하며 결정론적 폴백을 제공합니다.
